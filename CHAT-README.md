# Свои — приложение для вашей компании

Настольный клиент для Windows 10/11 x64 и общий сервер: переписка в реальном времени, текстовые и голосовые каналы, история сообщений, реакции, поиск в загруженной истории, индикаторы набора и участники в сети. Интерфейс на русском, работает также в браузере и на телефоне. Исходная игра в `index.html` и `campaign.html` сохранена отдельно.

## Для друзей на Windows

1. Распакуйте **весь** архив `dist/Svoi-1.0.0-win32-x64.zip`.
2. Запустите `Svoi-win32-x64/Svoi.exe`.
3. Вставьте приглашение от владельца, например `https://chat.example.com/?invite=…`.
4. Выберите имя. Для голосового канала разрешите доступ к микрофону.

Сменить сервер — `Ctrl + Shift + S` или меню «Свои». Клиент запоминает сервер и профиль. Это переносимая сборка без установщика и цифровой подписи. Windows-сборка подготовлена из официального Electron с проверкой контрольных сумм; запуск самой Windows-сборки требует проверки на Windows. В Linux проверен запуск Electron, подключение к серверу и изоляция интерфейса от Node.js.

**Одного клиента недостаточно для связи из разных домов.** Всем нужен доступ к одному работающему серверу по HTTPS. Локальный адрес владельца `localhost` не работает на компьютерах друзей. Хостинг в этой задаче ещё не развёрнут.

## Запуск сервера у владельца

Нужен **Node.js 24+**. На Windows можно запустить `START-SERVER.cmd`. Или в терминале в корне проекта:

```sh
npm ci --omit=dev
npm start
```

Откройте `http://localhost:3000` в браузере или настольном клиенте. При первом локальном запуске создайте компанию и профиль владельца. Затем нажмите «Позвать друзей». Чтобы ссылка работала у друзей, сервер должен быть доступен по общему HTTPS-адресу; создавайте приглашение, открыв именно этот адрес.

Для первой настройки удалённого сервера или восстановления доступа владельца выполните на сервере:

```sh
npm run setup-link
```

Откройте выданную **приватную** ссылку, заменив `http://localhost:3000` на адрес сервера. Не передавайте эту ссылку друзьям: она восстанавливает владельца. Для друзей используется обычное приглашение внутри приложения.

Профиль участника хранится в защищённой HttpOnly-cookie на 30 дней. Паролей и почты в этой версии нет. Очистка данных клиента или выход требуют нового приглашения и нового имени; старые сообщения остаются. Приглашение открывает всю историю и все каналы. Заменить приглашение может владелец; уже вошедшие участники сохранят доступ.

## Постоянный сервер в интернете

В корне подготовлен `render.yaml` для Render. Это **платный** web service с постоянным диском, чтобы история не пропадала при перезапусках. Стоимость нужно проверить перед созданием; ничего не размещено и платный тариф не подключён.

1. Загрузите исходники из этой рабочей копии в свой GitHub-репозиторий. Не загружайте `.data`, `node_modules` или `dist`: они уже исключены в `.gitignore`. До загрузки новых файлов в GitHub Render увидит только прежнюю игру.
2. В аккаунте Render выберите **New → Blueprint**, подключите этот репозиторий и проверьте тариф из `render.yaml`. Запустите создание сервиса только после проверки стоимости.
3. После успешного запуска откройте **Shell** сервиса и выполните `npm run setup-link`. Откройте приватную ссылку из вывода и создайте свою компанию. Не публикуйте эту ссылку.
4. Внутри чата нажмите «Позвать друзей». Вставьте это приглашение в Windows-клиент и отправьте друзьям вместе с клиентом.

HTTPS и WebSocket предоставляет Render; собственный домен необязателен. Учётные данные для Render в код не добавляются. Эта конфигурация ещё не проверена реальным развёртыванием в вашем аккаунте. Для голосовых звонков между сложными сетями может дополнительно понадобиться TURN.

Нужен Linux VPS или Node-хостинг с постоянным диском и поддержкой WebSocket. GitHub Pages обслуживает только статические файлы и для сервера чата не подходит. Настройте HTTPS reverse proxy к Node-процессу, перенаправляя HTTP Upgrade для `/ws`, и автоматический перезапуск процесса. Например, у Caddy достаточно:

```caddyfile
chat.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

Домен должен указывать на VPS, порты 80 и 443 должны быть доступны. Перед запуском за HTTPS задайте `COOKIE_SECURE=1`. Node-процесс по умолчанию слушает только `127.0.0.1`; для контейнерного хостинга задайте `BIND=0.0.0.0`. Не публикуйте порт с незашифрованным HTTP как адрес для клиентов.

| Переменная        | Назначение                                       | По умолчанию            |
| ----------------- | ------------------------------------------------ | ----------------------- |
| `PORT`            | Порт сервера                                     | `3000`                  |
| `BIND`            | Интерфейс прослушивания                          | `127.0.0.1`             |
| `DATA_DIR`        | Постоянный каталог базы и ключа владельца        | `.data`                 |
| `COOKIE_SECURE`   | `1` для сервера за HTTPS                         | выключено для localhost |
| `PUBLIC_URL`      | Общий HTTPS-адрес для команды `setup-link`       | `http://localhost:3000` |
| `RTC_ICE_SERVERS` | JSON-массив STUN/TURN-конфигураций для браузеров | Google STUN             |

База SQLite, WAL и ключ владельца находятся в `DATA_DIR`. Каталог не включён в Git и клиентскую сборку. Делайте резервные копии всего каталога при остановленном сервере; не публикуйте его. Нужен один процесс сервера: присутствие и голосовые комнаты пока хранятся в памяти одного процесса. Сообщения и сеансы переживают перезапуск. Проверка доступности — `GET /health`.

## Голос

Клиенты передают звук напрямую через WebRTC, сервер пересылает сигналы установления связи. Видео, демонстрация экрана и запись разговора в первую версию не входят. Работают выключение микрофона, отключение звука и выход из канала. HTTPS нужен для доступа к микрофону, кроме локального `localhost`.

В некоторых сетях прямой WebRTC не проходит: для них администратор задаёт рабочий TURN в `RTC_ICE_SERVERS`. Например, конфигурация имеет вид массива объектов `{ "urls": "turns:ваш-turn-сервер:5349", "username": "…", "credential": "…" }`; реальные значения вводятся в окружении сервера, не в Git. TURN-пароль передаётся вошедшим клиентам для установления соединений. Для постоянного публичного сервера предпочтительны временные TURN-учётные данные. Межсетевой звонок нужно проверить после развёртывания на выбранном хостинге.

## Разработка и сборка

```sh
npm ci
npm run dev
# Отдельный терминал:
npm run desktop
npm test
npm run desktop:build:win
```

Сборка создаёт переносимую папку, ZIP и файл SHA-256 в `dist/`. На Linux нужен `zip`, на Windows используется встроенный `tar.exe`. Electron и сервер не требуют сборки интерфейса. Скачать Electron в окружении с HTTPS-прокси можно командой `NODE_USE_ENV_PROXY=1 node node_modules/electron/install.js` (Bash); сохраняйте проверку TLS и контрольных сумм. `npm ci --omit=dev` устанавливает только зависимость сервера `ws`.

`npm test` запускает отдельный сервер и двух WebSocket-клиентов в изолированной временной базе. Проверяются приглашения, защита от запросов с другого сайта, сообщения, реакции, права владельца, сигналы голоса, удаление и сохранность после перезапуска. Проверка передачи звука и запуска `.exe` не подменяется этими тестами.

При подготовке дополнительно проверены два независимых браузерных профиля: приглашение, переписка, реакции, поиск, создание каналов, безопасный вывод HTML, удаление, сохранение профиля и мобильная навигация. В двух окнах Electron на одной машине проверены настоящий WebRTC-звонок с тестовыми микрофонами, полученные аудиодорожки и входящие аудиопакеты. Это не проверка межсетевого звонка или запуска `.exe` на Windows.

Это первая версия для небольшой компании: одно пространство, общие каналы и вход по приглашению. Личные переписки, файлы, блокировка участников, редактирование сообщений и полноценные аккаунты с восстановлением пароля пока не реализованы.
